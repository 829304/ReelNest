# 前端性能补充检查

继演员/详情加载优化后，继续检查大库操作、选择态、缓存播放与筛选。只读对照原版 `AppState+BatchSelection.swift`、`VideoCacheMenuItems.swift`、`VideoCacheDownloadController.swift`；不改变产品布局、批量操作范围、排序或缓存保护规则。

## 本轮已修复

1. **单条及批量操作读取全库**：`EmbyLibraryRepository.targets` 原先对评分、想看、标记观看等操作读取并解码整个来源。新增定向选择查询，只返回所选项；需要后代时用递归 CTE 沿现有 `media_parent` 索引展开。保留输入顺序、标题顺序、去重、跨来源拒绝、缺失条目校验和事务回滚。JSON 参数支持超过 SQLite 常规参数数量上限的选择，递归 UNION 可终止异常父子循环。
2. **系列缓存菜单/入队扫描全库**：只按来源和父 ID 查询该系列单集，使用现有父索引，返回字段与排序保持一致。
3. **选择态重绘构建全库集合**：改用快照已有的 ID 索引检查已选择项，不再每次重绘遍历所有条目。
4. **缓存播放检查所有文件**：获取播放租约前后的两次清单读取都只查询目标视频，保留文件真实性、路径边界、大小和事务内再次校验。无关损坏清单不会阻塞当前正常缓存；选到损坏条目仍拒绝。
5. **仅看已缓存筛选**：按缓存 ID 从快照索引查其所属系列，减少一次全库父级扫描；身份始终包含来源，避免同 ID 跨来源匹配。

## 查询计划与测量

以本机 92,130 条索引只读测量（`mode=ro`、`query_only`，未输出作品/账号/凭据）：

- 原全来源联表查询一次返回 92,130 行，约 917 ms，尚未计入 Dart JSON 解码。
- 初步增加 ID 条件后，SQLite 仍为标题排序选择 `media_title` 并扫描来源，单项约 47 ms。最终让选择 ID 作为 CROSS JOIN 的外层，实际计划变成按 `(source_id, local_id)` 主键查找。
- 最终定向单条读取连续 100 次约 11.39 ms，每次仅一行。与上面的单次测量热缓存条件不同，不能作为整页固定提速倍数。
- 单集查询原计划同样可能使用标题索引；现显式使用项目已存在的 `media_parent`，未变更 schema。

## 后续性能方向（尚未实现）

`sourceChangesProvider` 的全局通知会让 `embyVideoSnapshotProvider` 重建来源的全量快照。进度/想看等小变更因此仍可能产生全库读取。后续宜区分结构、元数据、观看状态变化，做局部更新；必须覆盖跨窗口播放进度、删除、同步、筛选及排序刷新一致性，不能简单关闭失效通知。

大库搜索/筛选现已使用后台 isolate，本轮没有重复改造。完整视频缓存清单的文件检查对磁盘失联和清理有必要，仅把明确的单视频播放路径收窄；全清单的后台批量校验仍可后续测量。

这不是全部前端或三个桌面平台的最终性能验收。未更改数据库结构、删除用户数据、修改原仓库或提交代码。
