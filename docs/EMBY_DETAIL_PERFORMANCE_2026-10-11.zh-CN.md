# 演员作品与详情加载优化

用户反馈：点击演员后作品集很慢，详情页演职人员、海报等元数据也很慢。本轮只调整读取、排队与缓存，不改变原版卡片尺寸、详情结构、完整作品范围或最终排序。已只读对照原 `PersonDetailView.swift`、`MediaTMDBExtrasView.swift` 的缓存先呈现、库中作品与演职人员/艺术照结构。

## 瓶颈与修改

- `SourceRepository.source(id)` 原先调用全量 `sources()`，每次都连接媒体表、统计所有来源。Emby 每张图片和详情请求前后均会检查来源，因此大库计数被重复执行。现在按 ID 查来源，内部连接/范围检查使用 `includeCounts: false` 只读取实时配置；UI 默认仍获取准确数量，不缓存登录状态，也不跳过来源删除检查。
- 演员查询原先等待所有库、所有分页完成后一次显示。现在每个已校验、已入库分页都会产生独立的排序快照；继续查询全部所选视频库，去重、客串单集归属系列和最终排序不变。后续失败保留已加载作品并提示重试，完整响应才可替换缓存。最近 16 个人物、每人至多 1000 部作品保留会话缓存，选库或同步版本改变即失效；每次进入仍查询服务器。
- 本地人物缓存筛选移到 SQLite JSON 查询，仅返回匹配的条目 ID，不再把全部详情 JSON 传回 UI isolate 后逐一解码。
- 详情图片可优先于排队海报，重复请求仍合并并可提升优先级。网络总并发仍最多 4；全库预热改为单个后台 worker，给当前页面留下下载槽位。
- 图片写盘原先每张都在数据库写锁中遍历缓存目录。现在每次检查容量/数量，超预算立即清理；未超预算时完整目录清理最多每分钟一次，首次及替换损坏缓存仍清理。容量上限和损坏图片重试行为保持。

## 测量与回归

只读打开本机 SQLite（`mode=ro`、`query_only`），包含 92,130 条媒体。相同进程预热后连续运行 100 次：

| 查询 | 总耗时 |
| --- | ---: |
| 原全部来源计数 | 21,953.52 ms |
| 新按 ID 配置读取 | 9.16 ms |

这是数据库查询对比，不是整页或服务器响应速度。没有访问或输出用户凭据、影片名称，也没有修改用户数据。

- 全量 `flutter test`：418 项通过。
- 最后补强后台预热测试后，浏览/图片缓存定向 40 项再次通过：阻塞后续演员分页时首批已可见；后页失败保留首批；近期作品缓存复用及选库失效；详情图片优先和重复请求合并；后台预热阻塞时详情图片独立完成；预算、损坏缓存及取消等既有回归。
- 三万条临时后台数据库中，100 次配置读取约 23 ms（测试环境记录，不作绝对时间断言）。
- `flutter analyze`：无问题。
